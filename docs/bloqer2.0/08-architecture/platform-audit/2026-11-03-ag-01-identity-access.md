## 2. Alcance y recorridos

El inventario AG-00 asigna a AG-01 **27 páginas y 2 handlers primarios**. Se revisaron contratos de entrada y servicios; esos números son inventario, no páginas navegadas. Se incluyeron consumidores compartidos de ACL en shell de proyecto, Field, Pendientes, campana y AI por dependencia comprobada. Su revisión operativa completa sigue en sus etapas.

1. **Identidad:** formularios `/login`, `/registro`, verificación/recuperación/reset → acciones y validators → `credentials-auth.service` → User/VerificationToken → callbacks Auth.js → `getSession` → gate de cuenta/epoch → contexto de tenant. Casos de token único, cooldown, suspensión concurrente y Google verificado; OAuth y email reales no ejecutados.
2. **Contexto:** preferencia de tenant → `getSessionTenantContext` → membresía ACTIVE con roles → tenant ACTIVE → empresa explícita válida o fallback D-092. Membresía inválida no se convierte en global ni habilita otro onboarding; las invitaciones a otros espacios se conservan.
3. **Acceso a obra:** layout/API shell/listado/ID/mutación → capability/gate del área → tenant + empresa + ProjectMembership → consultas limitadas antes de paginar/agregar. Incluye empresa compartida null, administración anclada y modo global/restringido.
4. **Asignaciones:** Equipo → editor/acciones → `project-membership.service` → lock tenant → lectura/intersección/diff → cambio y AuditLog en transacción → invalidación de modo tras commit. Reemplazo parcial conserva grants no mostrados.
5. **Configuración:** General/Equipo/Permisos/Políticas → acciones/validators → servicios de settings/equipo/policies/logo → empresa/tenant/membresía → auditoría y revalidación. Getters usados por la operación conservan acceso cuando se apaga la administración de configuración; las mutaciones aplican su flag y los IDs respetan empresa/ACL.
6. **Invitaciones:** creación tenant o plataforma → normalización, empresa/roles y lock común → una PENDING → email después de commit; aceptación pública con sesión/email/token → estado final/membresía/auditoría atómicos. Expiración permanece confirmada aunque aceptar/cancelar rechace el enlace.
7. **Plataforma:** sesión → autoridad PlatformAdmin/allowlist → tenants/users/modules/settings/vencimientos/registro. Nunca deriva permisos de plataforma desde OWNER del tenant. Extensiones simultáneas suman ambos incrementos; atención no pierde organizaciones después de la fila 300.
8. **Avisos y Field:** sus consultas reutilizan el alcance central; preferencia obsoleta no permite ver cronograma ajeno; revocar una obra oculta también sus avisos previos. Destinatarios deben conservar membresía/empresa válidas.

Se inspeccionaron rutas/acciones/invalidaciones y contratos Zod/DTO. La verificación SQL ejecuta servicios reales y restricciones de DB. La revisión de etiquetas, formularios y estados de pantalla fue estática; no acredita responsive, contraste o apariencia final.

## 3. Hallazgos y correcciones

Los identificadores siguientes agrupan una causa y sus consumidores. No se contaron otra vez los seis hallazgos de AG-00.

- **GA-AG-01-001 · P1 · JWT de Credentials posterior a reset.** El callback reemplazaba el epoch autenticado con una lectura más reciente de User; un login con la clave anterior podía recibir el epoch nuevo. `session-password-epoch` conserva el valor que realmente autenticó Credentials. Regresión del callback/helper y gate existente.
- **GA-AG-01-002 · P1 · Reactivación involuntaria de cuenta.** Verify/reset/takeover y eventos de Google podían sobrescribir suspensión concurrente por actualizaciones basadas en una lectura anterior. Se usan predicados de estado y comprobación del resultado; Google exige `email_verified === true`. Tests unitarios y SQL intercalan suspensión entre lectura y escritura. No se afirma explotación observada en Google real.
- **GA-AG-01-003 · P2 · Tokens y bloqueo invertido.** Emisión leía/borraba/creaba fuera de una sección serializada y podía duplicar tokens/evitar cooldown; consumo y takeover podían tomar locks en orden inverso. Emisión/verify/reset/takeover comparten advisory por email y revalidan expiración después de esperar. SQL prueba concurrencia y consumo único.
- **GA-AG-01-004 · P2 · Contraseñas Unicode truncadas.** El máximo de caracteres no limitaba los bytes que acepta bcrypt. Registro/reset validan 72 bytes UTF-8; login conserva compatibilidad histórica. Se actualizaron hints y ayuda. Tests ASCII/acentos/emojis/límite.
- **GA-AG-01-005 · P1 · Anclaje inválido ampliaba sesión.** Una empresa explícita inexistente/inactiva/ajena terminaba en companyId null, que significa global. Ahora se descarta esa membresía para sesión; se prueban fallback válido y membresía sin roles. El onboarding informa acceso no disponible, conserva invitaciones y ofrece cerrar sesión.
- **GA-AG-01-006 · P1 · IDs y shell de proyecto.** Shell/cliente y varias mutaciones comprobaban solo tenant; el ACL central tampoco comprobaba empresa. `requireProjectAccess`/`canAccessProject`, scope, shell, ID, listados y lifecycle intersectan empresa y ACL; null compartido sigue permitido. SQL usa dos tenants, dos empresas, obra compartida y ambos modos. El alta de factura desde certificación usa esos helpers mínimos para sus datos fiscales: no depende de obtener el registro completo del módulo Proyectos cuando AR está habilitado.
- **GA-AG-01-007 · P1 · Preferencia y pendientes de Field.** Un proyecto preferido podía saltar la asignación; consultas/conteos omitían empresa. Preferencia, agenda, pickers y pendientes usan alcance vigente antes de consultar. SQL negativo y positivo, incluida preferencia revocada.
- **GA-AG-01-008 · P1 · Avisos fuera de alcance actual.** Campana/inbox y sus mutaciones podían conservar datos de obras revocadas o de otra empresa; fan-out omitía algunos controles. Se limita lectura/mutación y audiencia por tenant, destinatario, empresa y ACL, aplicando D-092. SQL comprueba revocación posterior a entrega.
- **GA-AG-01-009 · P1 · Administración de asignaciones.** El editor revelaba empresas ajenas; reemplazos leían el diff fuera de transacción y logs podían fallar después del cambio. Ahora editor y destino se intersectan; lock/lectura/diff/cambio/log son atómicos. Se conservan asignaciones ocultas/canceladas. SQL prueba reemplazos paralelos, importación y rollback de cinco mutaciones.
- **GA-AG-01-010 · P1 · Último propietario.** Dos demociones/desactivaciones podían dejar cero OWNER; una cuenta suspendida contaba como reemplazo. Equipo y estado global usan el mismo lock tenant y cuentan cuentas+membresías ACTIVE. SQL prueba las tres combinaciones concurrentes y el segundo propietario suspendido; plataforma expone también el estado de cuenta para recuperar acceso.
- **GA-AG-01-011 · P1 · Invitaciones concurrentes y expiración.** Creación tenant/plataforma podía duplicar PENDING; cancelar/aceptar/cambiar tenant y auditar no compartían una sección atómica. Se unificó el lock y se releyó el estado. La transición EXPIRED se confirma antes de devolver conflicto. SQL cubre creación mixta, email incorrecto, reuso, cancelación/aceptación y vencidos.
- **GA-AG-01-012 · P2 · Configuración incompleta o perdida.** Null explícito de sitio/IVA se convertía en undefined; la empresa editable ignoraba anclaje; notas parciales podían pisarse y auditoría fallar después de guardar. Se conserva null, se limita empresa y se serializa lectura/merge/cambio/log. SQL verifica persistencia, dos notas paralelas y rollback de empresa+tenant; se aplicó atomicidad a altas legacy de tenant/empresa/membresía.
- **GA-AG-01-013 · P2 · Seguimiento SaaS.** Extensiones leían fecha antes del lock y perdían un incremento; atención cortaba en 300 antes de filtrar y el redondeo de días podía clasificar un trial recién vencido como por vencer. Lectura/cálculo bajo lock, predicados en DB sin corte prematuro y cálculo consistente. Se incluyen cuentas suspendidas en la detección de falta de propietarios. SQL prueba más de 300 organizaciones e incrementos simultáneos.
- **GA-AG-01-014 · P2 · Límite público del servicio de usuarios.** Varias funciones devolvían User completo; perfil no exigía cuenta/tenant/membresía activos ni auditoría atómica. DTO selecciona campos públicos y la mutación valida actividad y registra dentro de transacción. La acción actual ya descartaba el resultado: **no se confirmó fuga de hashes al navegador**. Estado global no tiene consumidor web actual.
- **GA-AG-01-015 · P2 · Logo y limpieza.** Pointer y auditoría separados, snapshots previos y cleanup concurrente podían dejar inconsistencia. Upload único antes de transacción; lectura+pointer+log bajo lock; limpieza después de commit y compensación solo si el nuevo objeto no está vigente. Ante commit incierto o DB inaccesible se conserva el objeto. Ocho tests con SDK R2 sustituido; no hubo R2 real.
- **GA-AG-01-016 · P1 · Disponibilidad distinta de la navegación.** Entradas directas y formularios de proyectos/configuración/policies/avisos no siempre aplicaban el flag. Se combinaron rol+flag en servidor/UI, preservando lecturas operativas, perfil personal, aceptación pública e independencia de plataforma. Shell admite AP habilitado con PROJECTS apagado; NOTIFICATIONS off compone lecturas vacías. Tests unitarios y SQL de las ramas correspondientes.
- **GA-AG-01-017 · P2 · Alta de organizaciones con igual nombre.** Actores distintos podían elegir el mismo slug entre consulta e inserción. Bundle compartido serializa por base de slug; onboarding y provisión admiten espera acotada de transacción (30 s). La prueba SQL encontró el timeout implícito de 5 s; corregido y repetido, incluido onboarding contra provisión de plataforma.
- **GA-AG-01-018 · P3 · Terminología de administración.** Estados/roles técnicos aparecían sin traducir y la empresa automática se llamaba «Sin asignar». Se reutilizaron labels españoles, se aclaró **Automática si hay una sola empresa**, y acceso global conservando alcance de empresa. Tipos/lint y revisión de código; apariencia en navegador no ejecutada.
- **GA-AG-01-019 · P2 · Filtros de registro producían error de servidor.** URL con tenant inválido/límite fraccional o fuera de rango llegaba como excepción de validación. El parser usa el schema canónico, mantiene una consulta inválida sin ejecutar y muestra feedback; pruebas de valores válidos, repetidos y malformados.
- **GA-AG-01-020 · P2 · Destino inseguro de fixtures D-111.** Suites opt-in aceptaban desarrollo normal por fragmentos de URL y fallback `.env`; sus fixtures modifican estados/contraseñas sintéticas y no debían ejecutarse allí. Exigen ahora base aislada explícita, host exacto, ambas URLs e identidad SQL; liberan conexión al terminar. Se reutiliza guard mantenido con regresiones, sin scripts de parche.
- **GA-AG-01-021 · P2 · Ciclo de imports de política de email.** Importar el servicio directamente recorría runner→alertas→email→constante aún no inicializada. El servicio de política usa RBAC puro con el mismo conjunto actual de actores y elimina ese ciclo. Prueba de importación/uso y getters con configuración apagada.

Fuentes principales: `packages/auth/src/auth.ts`; servicios `auth`, `security`, `project`, `membership`, `company`, `tenant-settings`, `platform`, `user`, `onboarding`, `field`, `notifications`; mutaciones de políticas en `budget`/`procurement`; validators de credentials/settings; páginas Configuración/plataforma y ayuda.

### Rectificaciones y límites del diagnóstico

- Se retiró el supuesto de ausencia de feedback al guardar: `SearchParamsToast` ya estaba montado en ambos shells. No se dejaron avisos duplicados ni se contabiliza como defecto.
- La primera expectativa SQL de metadata de settings asumía objeto anidado; el sanitizador documentado guarda un string JSON acotado. Se corrigió la prueba, no se cambió ese contrato.
- El diagrama funcional de User incluía ARCHIVED/CANCELLED que no existen como valores del enum técnico actual. Se documentó explícitamente objetivo frente a implementación, sin agregar estados ni equiparar una membresía con una cuenta. El archivado funcional sigue sin pantalla/implementación y requiere decisión futura.
- El cache de modo de proyecto mantiene su TTL existente de 5 s entre instancias; los cambios confirmados invalidan el cache local tras commit. No se introdujo infraestructura de invalidación distribuida.
